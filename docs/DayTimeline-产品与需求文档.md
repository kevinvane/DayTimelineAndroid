## 1. 文档说明

### 1.1 本文档要解决的问题

当前需要一个可嵌入任意 Android 应用的单日时间轴组件，用于展示一天的日程，并支持用户直接在新组件上完成查看、新建、调整、删除的全流程操作。

市面上已有的开源实现普遍存在三类问题：**数据模型不贴合真实日程**（用「第几节课」这类序号代替时间）、**重叠日程显示错乱**、**交互体验粗糙**。本文档定义一个从零构建的新组件，明确它**要做什么**、**长什么样**、**怎么用**、**做到什么程度算完成**。

### 1.2 文档边界

| 属于本文档 | 不属于本文档 |
|---|---|
| 产品定位与目标 | 技术架构设计 |
| 功能需求与优先级 | 代码实现方案 |
| 界面与交互规格 | 数据库设计 |
| 数据契约（对外约定） | 接口协议定义 |
| 质量要求与验收标准 | 具体排期与人力安排 |
| 版本规划 | 商业推广计划 |

> 技术实现细节由研发另行输出技术方案文档，本文仅以「技术要求」形式约定**必须达成的效果**，不约束实现方式。

### 1.3 需求优先级说明

| 级别 | 含义 | 判定标准 |
|---|---|---|
| **P0** | 必须有 | 缺失则组件无法交付 MVP |
| **P1** | 应该有 | 缺失影响可用性，但不阻塞上线 |
| **P2** | 可以有 | 锦上添花，可延后到后续版本 |

### 1.4 术语约定

| 术语 | 含义 |
|---|---|
| **组件** | 本产品对外提供的时间轴视图控件 |
| **时间格** | 一小时对应的一行，组件的基本刻度单位 |
| **刻度线** | 每小时的分隔横线，24 小时共 25 条 |
| **时间轴区域** | 屏幕左侧显示时间文字的固定宽度区域 |
| **语义色项** | 产品定义的「这块界面用哪一类颜色」，具体色值由设计规范给出 |
| **日程块** | 一个日程在时间轴上的可视化色块 |
| **轨道** | 横向分栏的列，用于让时间重叠的日程并排显示 |
| **浏览态** | 用户查看日程、未选中任何日程的状态 |
| **编辑态** | 某个日程被选中、可调整的临时状态 |
| **选中态** | 日程被选中时的强调视觉，与「编辑态」（临时可调整）不同 |
| **当前时间线** | 标示「此刻」位置的水平红线 |
| **吸附** | 拖拽时时间自动对齐到整刻度（如每 15 分钟） |
| **接入方** | 使用本组件的业务应用 |

## 2. 产品概述

### 2.1 一句话定义

**DayTimeline** 是一个可嵌入任意 Android 应用的**单日 24 小时时间轴组件**，以「纵向时间 + 横向重叠分栏」的方式呈现一天的日程，并让用户直接在新组件上完成查看、新建、调整、删除操作。

### 2.2 产品形态

```
┌──────────────────────────────────────────┐
│  ← 设备屏幕（竖屏）                        │
├────┬─────────────────────────────────────┤
│    │ 00:00 ─────────────────────────────  │  ← 刻度线 + 左侧时间文字
│ 时 │                                     │
│ 间 │      ┌──────────┐                   │
│ 标 │      │ 日程 A   │                   │
│ 签 │      │ 09:00    │                   │
│    │      │   10:30  │                   │
│ 栏 │      └──────────┘ ┌──────┐          │  ← 时间重叠时横向并排
│    │                   │ 日程 B│          │
│    │                   └──────┘          │
│    │  ●━━━━━━━━━━━━━━━━━━━━━━━━━━         │  ← 当前时间线（红）
│    │                                     │
│ 12 │      ┌───────────────────────┐      │
│ :00│      │ 日程 C（已过，浅底灰字）│      │
│    │      └───────────────────────┘      │
│    │                                     │
│ 24 └─────────────────────────────────────┘
└────┴─────────────────────────────────────┘
```

**三个核心特征**

| 特征 | 说明 |
|---|---|
| **纵向是时间** | 从 00:00 到 24:00 自上而下，每小时一格 |
| **横向是并列** | 时间相互重叠的日程自动并排，不会互相遮挡 |
| **可直接操作** | 长按或点空白即进入编辑态，拖拽调整时间，无需跳转其他页面 |

### 2.3 差异化定位

| 对比对象 | 形态 | 数据模型 | 拖拽编辑 | 接入成本 | 依赖负担 |
|---|---|---|---|---|---|
| 通用日历 SDK | 月/周/日多合一 | 时间戳 | 多数不支持 | 体积大、约束多 | 重 |
| 通用课程表控件 | 固定网格（如 7 天 × 12 节） | 课节序号 | 不支持 | 轻 | 轻 |
| **DayTimeline** | **单日时间轴** | **真实时间（几点几分）** | **支持** | **轻** | **无第三方依赖** |

### 2.4 命名与品牌

| 项 | 值 |
|---|---|
| 产品名 | DayTimeline |
| 一句话描述 | 单日 24 小时时间轴日程组件 |
| 许可协议 | Apache-2.0（发布时须完整填写版权人信息） |

## 3. 产品目标与非目标

### 3.1 产品目标

| 编号 | 目标 | 衡量指标 |
|---|---|---|
| G1 | 业务方无需自行实现时间轴即可接入 | 接入步骤不超过 6 步（§9.2），业务方开发者 5 分钟内完成首个可用页面 |
| G2 | 重叠日程显示正确 | 任意重叠组合下无视觉遮挡（见 §14 验收） |
| G3 | 编辑交互完整可用 | 新建、调整、取消、删除四条路径全部走通 |
| G4 | 性能满足商用要求 | 100 条日程下滚动流畅无卡顿（见 §12.1） |
| G5 | 接入方无负担 | 不引入任何第三方依赖 |
| G6 | 视觉可定制 | 更换配色与布局无需改动业务代码 |
| G7 | 质量可保障 | 核心逻辑测试覆盖率不低于 90%；可测逻辑覆盖率不低于 75%（§12.4.1） |

### 3.2 非目标（明确不做）

| 编号 | 不做的事 | 理由 |
|---|---|---|
| N1 | 月视图、周视图 | 超出「单日时间轴」定位，如需另立项目 |
| N2 | 日程数据存储、同步、网络请求 | 属于业务层职责，组件只负责展示与交互 |
| N3 | 账号、登录、云端日历 | 同上 |
| N4 | 重复日程规则（每周三、每月 1 号等） | 规则复杂，建议由业务层展开为具体日程后再传入 |
| N5 | 日程提醒、闹钟、通知 | 属于业务层与系统能力 |
| N6 | 时间跨天、跨时区切换 | v1.0 聚焦单日；跨天由业务层切换日期实现 |
| N7 | 多设备时间同步 | 组件使用设备时间，业务如有需要可自行指定 |
| N8 | 图形化搭建工具 | 面向研发，不面向产品运营 |

## 4. 目标用户与使用场景

### 4.1 用户角色

| 角色 | 特征 | 核心诉求 |
|---|---|---|
| **终端用户** | 企业员工、服务业从业者、预约类 App 使用者 | 快速看清今天要做什么，并顺手调整 |
| **业务开发者** | 需要在 App 内嵌入日程界面的研发 | 不想自己实现时间轴绘制、重叠排布、拖拽交互 |

### 4.2 用户故事

| 编号 | 用户故事 |
|---|---|
| US1 | 作为用户，我打开 App 就自动看到当前时间附近的内容，不用手动翻找 |
| US2 | 作为用户，我一眼就能分辨哪些日程已经过去、哪些还没开始 |
| US3 | 作为用户，我能看清时间互相重叠的几个日程，不会被遮挡 |
| US4 | 作为用户，我点一下空白处就能在那个时间点新建日程 |
| US5 | 作为用户，我长按一个日程就能调整它的时间，不用去详情页 |
| US6 | 作为用户，我拖动日程时能看到新的起止时间，不会拖错 |
| US7 | 作为用户，我调整错了可以取消，且不会误改我的数据 |
| US8 | 作为用户，我删掉一个日程后它就真的没了，且有二次确认防止误删 |
| US9 | 作为业务方，我换肤时只改资源文件，不改任何业务代码 |
| US10 | 作为业务方，我的日程数据有脏数据时，组件不会崩溃，只给提示 |
| US11 | 作为业务方，我能在组件上自定义每个日程块长什么样 |
| US12 | 作为业务方，我把组件放进可滚动容器里也不会出问题 |

### 4.3 核心场景与流程

#### 场景 A：查看当天日程

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| A1 | 打开页面 | 时间轴自动滚动到当前时间附近 |
| A2 | 上下滑动 | 流畅浏览 00:00–24:00 全天 |
| A3 | 观察日程块 | 已过 / 进行中 / 未到 三种视觉状态清晰可辨 |
| A4 | 点击某日程 | 触发业务方配置的点击事件 |

#### 场景 B：新建日程

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| B1 | 点击时间轴空白处 | 进入编辑态，色块出现在点击位置 |
| B2 | 观察色块 | 默认时长 1 小时，标出起止时间 |
| B3 | 上下拖动色块 | 起止时间随手指实时变化，时间自动对齐刻度 |
| B4 | 点击「完成」 | 新建事件通知业务方，色块固定 |
| B5 | （可选）点击「取消」 | 色块消失，不通知业务方 |

#### 场景 C：调整已有日程时间

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| C1 | 长按某日程 | 进入编辑态，色块高亮，标出当前起止时间 |
| C2 | 上下拖动色块主体 | 整块时间平移，起止时间实时变化 |
| C3 | 点击「完成」 | 修改事件通知业务方 |
| C4 | （可选）点击「取消」 | 恢复原时间，不通知业务方 |

#### 场景 D：调整日程时长

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| D1 | 长按某日程 | 进入编辑态 |
| D2 | 拖动色块上边缘的手柄 | 开始时间提前，起止时间实时变化 |
| D3 | 拖动色块下边缘的手柄 | 结束时间延后 |
| D4 | 拖到边界 | 时间不会超出 00:00–24:00；短于最小时长时自动兜底 |
| D5 | 点击「完成」 | 修改事件通知业务方 |

#### 场景 E：删除日程

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| E1 | 长按某日程 | 进入编辑态 |
| E2 | 点击删除入口 | 弹出二次确认 |
| E3 | 确认 | 删除事件通知业务方，色块消失 |
| E4 | 放弃 | 回到编辑态，数据不变 |

#### 场景 F：数据更新

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| F1 | 业务方数据变更后提交新列表 | 界面增量刷新，**不闪烁、不重排、滚动位置不跳变** |
| F2 | 单条日程内容被修改 | 仅该块更新，其余不动 |
| F3 | 单条日程被删除 | 仅该块消失，其余不动 |

#### 场景 G：切换日期

| 步骤 | 行为 | 预期结果 |
|---|---|---|
| G1 | 业务方调用切换日期 | 时间轴按新日期刷新 |
| G2 | 新日期是今天 | 显示当前时间线 |
| G3 | 新日期不是今天 | 隐藏当前时间线 |

## 5. 形态借鉴与必须规避的问题

本章说明本产品的形态来源与质量底线。

### 5.1 借鉴的成熟形态

| 编号 | 借鉴内容 | 理由 |
|---|---|---|
| K1 | 单日纵向时间轴，1 小时一格 | 已被多个主流日历应用验证，用户零学习成本 |
| K2 | 数据模型直接使用「几点几分」 | 贴合真实业务语义，杜绝单位混淆 |
| K3 | 重叠日程横向分栏 | 日程场景刚需 |
| K4 | 当前时间线 + 定时刷新 | 日程场景刚需 |
| K5 | 三段式交互：点=查看 / 长按=编辑 / 拖拽=调整 | 交互层次清晰，不易误操作 |
| K6 | 时间吸附（默认每 15 分钟） | 拖拽手感的决定性因素 |
| K7 | 已过 / 进行中 / 未到 三态样式 | 用户最关心的信息前置 |
| K8 | 编辑态实时显示起止时间 | 大幅降低拖拽误操作 |
| K9 | 数据与视图解耦的业务方契约 | 组件不侵入业务模型 |
| K10 | 零第三方依赖 | 降低接入方体积与冲突风险 |

### 5.2 必须规避的质量问题

以下问题在同类开源实现中被实际发现。**本产品不得重现**。

| 编号 | 问题 | 用户可感知的业务后果 | 本产品的硬性要求 |
|---|---|---|---|
| **D1** | 重叠分栏计算错乱 | 多组日程同时重叠时，色块互相遮挡或过窄，用户看不清自己的安排 | 分栏必须满足：① 任意两组时间重叠的日程永不互相遮挡；② 所需列数等于最大同时重叠数；③ 前序日程结束后的空余列必须被后续日程复用；④ 列分配只取决于时间重叠关系，与传入顺序无关；⑤ 宽度分配必须符合 §7.9 的 W1–W6 |
| **D2** | 数据下标越界 | 删除或刷新后，偶发闪退 | 任何列表操作都不得导致崩溃 |
| **D3** | 取消操作被当成确认 | **用户误改数据且无法察觉**——最严重问题 | 用户点击取消后，**绝对不得**向业务方发出任何数据变更通知 |
| **D4** | 首帧尺寸计算错误 | 首次显示瞬间色块错位跳动 | 任何情况下色块尺寸不得为负；首次显示不得抖动 |
| **D5** | 时间判断精度问题 | 「仅今天显示当前时间线」功能完全失效 | 时间判断必须准确可靠，不受刷新时机影响 |
| **D6** | 强依赖特定外层容器 | 放入其他容器直接崩溃 | 组件必须同时支持「自身滚动」和「外部容器滚动」两种模式，且不崩溃 |
| **D7** | 无法定制 | 业务方想改色块样式必须复制源码改造 | 必须提供定制入口，改样式无需改源码 |
| **D8** | 尺寸定义多处重复 | 改一处漏一处，界面错乱 | 所有尺寸、颜色、文案必须集中管理且单一来源 |
| **D9** | 深色模式不生效 | 夜间使用刺眼或看不清 | 全部颜色随系统主题生效，切换无需改代码 |
| **D10** | 无差别重复刷新 | 长时间使用后耗电、卡顿 | 仅在显示内容真正变化时才更新，不得周期性做无效刷新 |
| **D11** | 吸附上下不对称 | 往上拖和往下拖吸附表现不一致，手感别扭 | 吸附必须上下对称 |
| **D12** | 旋转屏幕丢失状态 | 转屏后滚动位置、日期全部重置 | 必须支持状态保存与恢复 |
| **D13** | 无法国际化 | 中文应用里出现英文时间格式或英文提示文案 | 时间格式与文案必须随系统语言变化 |
| **D14** | 无夜间配色 | 夜间模式下界面不可读 | 必须提供夜间配色 |
| **D15** | 无障碍缺失 | 视障用户完全无法使用 | 屏幕阅读器可逐条读出日程内容 |
| **D16** | 界面元素过度膨胀 | 简单界面产生大量无用元素，滚动掉帧 | 时间轴网格部分不得产生常驻界面元素 |
| **D17** | 无限重复布局 | 界面持续满负荷运行，手机发烫耗电 | **严禁**出现持续不收敛的重绘循环 |
| **D18** | 时间单位含义不明 | 业务方传错单位，色块高度差 60 倍 | 数据契约必须让「传错单位」在编译阶段就不可能发生 |
| **D19** | 数据类型约束松散 | 类型不匹配在运行期才暴露 | 数据契约必须提供编译期类型保障 |
| **D20** | 存在大量无用代码 | 后续维护成本高，容易改错 | 不得存在零调用的死代码，纳入自动化检查 |

### 5.3 默认参数的取值原则

全部默认值的**唯一定义处为 §7.2**（含「取值依据」列）。本节只补充三条跨维度的判断原则，避免多处重复定义导致改一处漏两处。

| 原则 | 说明 |
|---|---|
| **可点性优先于信息密度** | 任何触摸热区不小于 48dp；视觉元素可小，热区不得小 |
| **刷新越少越好** | 仅在显示内容真正变化时更新；当前时间线 30 秒刷新已足够 |

### 7.9 重叠日程的宽度分配策略

这是 FR-006 与 D1 ⑤ 的判定依据，必须在实现前定稿。

| 规则 | 说明 |
|---|---|
| **W1 总列数固定** | 全天需要的列数 = 任意时刻「最大同时重叠条数」。该列数对全天所有日程统一生效 |
| **W2 基准等分** | 每列基准宽度 = 可用宽度 ÷ 总列数，列与列之间留「日程块间距」 |
| **W3 允许向右扩展** | 若某日程右侧相邻列在其纵向范围内**没有任何日程**，允许它向右扩展占用这些空格 |
| **W4 扩展上限** | 单个日程最多扩展到占满整行 |
| **W5 不向左扩展** | 扩展只能向右，避免同一组重叠日程的列分配出现歧义 |
| **W6 左边界不变** | 扩展后左边界保持不动，仅向右变宽 |

**示例（假设某天共 2 列）**

| 场景 | 分栏 | 宽度结果 |
|---|---|---|
| A 09:00–12:00，B 10:00–11:00（互相重叠） | A 列 0、B 列 1 | A 占 1/2、B 占 1/2（B 与 A 重叠，A 不可扩展） |
| A 09:00–12:00，C 13:00–14:00（与 A 不重叠） | A 列 0（右侧列 1 在其范围内为空，可扩展）、C 列 0 | **A 占满整行、C 占满整行** |
| A 09:00–10:00，B 11:00–12:00（不重叠） | 都用列 0 | **两者都占满整行** |
| A 09:00–12:00、B 10:00–11:00、C 13:00–14:00 | A 列 0（可扩展）、B 列 1、C 列 0 | A 占满整行、B 占 1/2、C 占满整行 |
| A 09:00–12:00、D 13:00–14:00 占用列 0，E 10:00–11:00 占用列 1 | A 列 0（右侧列 1 被 E 占用，停止扩展） | A 占 1/2（不可越过被占用的列） |

> 第 2、3、4 行体现 W3 的价值：并不与任何日程重叠的条目可以占满整行，视觉上更清晰、信息密度更高。

## 8. 交互规格

### 8.1 交互状态流转

```
                    ┌───────────────────────────────────────┐
                    │            浏览态                      │
                    │  滚动 · 点击日程 · 长按日程              │
                    └──┬────────────┬─────────────┬─────────┘
         点击空白区域     │            │ 长按日程      │ 点击日程
         ↓               │            ↓             ↓
    ┌─────────────┐      │      ┌────────────┐   触发点击事件
    │ 新建编辑态   │      │      │ 编辑态      │  （状态不变）
    │ 默认 1 小时  │      │      │ 移动/改时长  │
    └──────┬──────┘      │      └──┬───┬───┬──┘
           │ 完成 ↓      │    完成 ↑ │   │ ↑ 取消
           │      ┌──────┴──────────┘   └─────┴──→ 浏览态
      触发新建事件      │
           │           │
           └───────────┘

   ⚠️ 硬性要求：任何「取消」路径都不得向业务方发出数据变更通知（D3）
```

### 8.2 手指操作流程

| 阶段 | 判定 | 行为 |
|---|---|---|
| 按下 | 落在编辑手柄上？ | 进入「调整时长」模式，记录起始基准 |
| | 落在编辑块上？ | 进入「移动」模式 |
| | 落在已有日程上？ | 记录为「待长按」 |
| | 落在空白处？ | 记录为「待长按 / 待新建」 |
| 移动 | 位移超过阈值（标准阈值的 0.3 倍） | 取消「待长按」，转为滚动；已进入编辑态则开始拖拽 |
| | 已进入拖拽且位置变化超过 1 像素 | 按吸附步长更新，**变化后才请求重绘** |
| | 拖到视口上下 48dp 范围内 | 启动自动滚动（P2） |
| 抬起 | 处于拖拽中 | 保留编辑态，等待用户确认或取消 |
| | 已触发长按但全程未移动 | **进入编辑态**（原地选中），等待用户确认或取消 |
| | 长按命中的是空白处 | 不进入编辑态（空白处不支持长按），等同普通点击 |
| | 未触发长按且位移很小 | 视为点击，触发点击事件 |
| | 未触发长按且点在空白 | 进入新建编辑态 |

#### 8.2.1 业务方接管后的退出路径（v1.3 新增）

当业务方按 §10.2 第四层接管编辑层（弹出自己的表单）时，**FI-010「点外部区域视为取消」不再由组件执行**：

| 情形 | 行为 |
|---|---|
| 未接管（默认） | 点编辑块外部 → 视为取消，语义与「取消」完全一致，不发出任何数据变更通知 |
| 已接管 | 点编辑块外部**不触发取消**。退出路径完全交给业务方，由业务方在表单关闭时调用「完成」或「取消」 |

**理由**：业务方接管后弹出的表单是**组件外部的窗口**。若表单非模态（外部透明可点），用户点击时间轴会触发 FI-010 → 组件取消编辑，而表单仍开着，随后业务方提交时草稿已失效——产生「表单开着但编辑态没了」的不一致状态。

**接管期间仍然允许拖拽**：拖拽只改草稿，最终以业务方提交时的值为准。

> **硬性要求（D3 不变）**：无论是否接管，「完成」都是唯一会发出数据变更的出口，「取消」都不得发出任何数据变更通知。

> **硬性要求（D17）**：界面刷新必须采用「变化检测」机制——只有显示内容真正变化时才请求重绘，**任何情况下不得出现持续不收敛的重复重绘**。

### 8.3 时间吸附规则

| 场景 | 规则 |
|---|---|
| 上下拖拽移动日程 | 起始时间对齐到吸附步长；结束时间跟随 |
| 拖拽上边缘 | 结束时间对齐；不得早于 00:00 |
| 拖拽下边缘 | 结束时间对齐；不得晚于 24:00 |
| 最短时长 | 自动兜底至最短时长（默认 5 分钟） |
| 最长时长 | 自动兜底至 24 小时 |
| 向上与向下 | **必须对称**（D11）：距刻度线向上 7 分钟与向下 8 分钟，吸附结果应一致 |
| 关闭吸附 | 步长设为 0 时不做对齐，但保留最短/最长时长兜底 |

#### 8.3.1 表单输入的时间合法化（v1.3 新增）

业务方表单一次可同时设定起止时间（§7.7.1）。**表单与拖拽必须走同一套规则**，由组件在接收提交值时统一合法化：

| 场景 | 规则 |
|---|---|
| 两端同时设定 | **两端用同一套规则吸附**，上下对称（D11）；不得只修一端 |
| 两端填反（结束早于开始） | 自动交换 |
| 短于最短时长 | 优先把结束时间往后推；越界则改为把开始时间往前拉 |
| 长于最长时长 | 从开始时间处截断 |
| 超出 `[00:00, 24:00]` | 钳制到范围内 |
| 合法化后必须满足 | `00:00 <= 开始 < 结束 <= 24:00`，且时长落在最短/最长之间 |

> 组件**不做**输入校验的提示或报错——合法化对用户不可见（与 §9.3 一致），修正后的值即最终结果。

### 8.4 边缘自动滚动（P2）

| 项 | 默认值 |
|---|---|
| 触发区域 | 视口上下各 48dp |
| 单次滚动量 | 8dp |
| 跟随对象 | **被拖动的日程块**（不是手指位置） |

### 8.5 滚动行为

| 项 | 规格 |
|---|---|
| 滚动范围 | 从 00:00 顶部到底部 24:00 之外留白处 |
| 首次定位 | 默认定位到「当前时间向上偏移约三分之一屏」 |
| 非今天 | 定位到 00:00（顶部） |
| 惯性 | 跟随系统原生手感 |
| 边界回弹 | 关闭（避免与拖拽手势冲突） |
| 状态恢复 | 旋转屏幕后恢复原滚动位置 |

### 8.6 两种滚动模式的行为差异

FI-001 / FI-002 提供的两种模式，在**高度约定、滚动归属、状态恢复**上行为不同，业务方必须按页面结构选择。

| 项 | 自身滚动（默认） | 外部容器滚动 |
|---|---|---|
| **组件高度约定** | **填满父容器**，高度由业务方决定 | **等于全天内容高度**（24 × 每小时格高 + 顶部留白 + 底部留白） |
| 滚动由谁负责 | 组件自身 | 外层滚动容器 |
| 是否消费垂直手势 | 是 | 否，必须让给外层容器 |
| 边界回弹 | 关闭 | 由外层容器决定 |
| 旋转后滚动位置恢复 | 组件自动恢复（D12） | **由外层容器负责**；组件只恢复「查看日期」等自身状态 |
| 适用场景 | 组件占满整个内容区 | 组件与其它内容（如顶部 Header）一起滚动 |
| 高度配置错误的后果 | — | 高度不足则 24 小时内容被截断；高度过大则下方留白过多 |

> **业务方须知**：外部滚动模式下必须按「全天内容高度」设置组件高度。组件不主动校验该高度，但 E12 / E13 验收会覆盖该场景。组件高度本身为可配置项（见 §10.1）。

## 9. 数据规格

### 9.1 数据契约（对外约定）

业务方提供的每条日程必须包含以下信息：

| 字段 | 含义 | 必填 | 约束 |
|---|---|:--:|---|
| 开始时间 | 当天的开始时刻 | 是 | 不得早于 00:00 |
| 结束时间 | 当天的结束时刻 | 是 | 必须晚于开始时间，不晚于 24:00 |
| 唯一标识 | 用于识别与定位 | 是 | 建议全局唯一 |
| 是否已过期 | 覆盖默认状态判断 | 否 | 缺省时由组件按当前时间自动判断 |
| 显示内容 | 色块上显示什么 | 由业务方自定 | 无格式限制；允许为空 |
| 业务色（v1.3） | 该日程块内强调色 | 否 | 缺省为 null，表示使用组件默认块配色；深浅适配责任在业务方（§7.7.1） |

**关键设计原则**

| 原则 | 说明 |
|---|---|
| 时间用「几点几分」表达 | 业务方不可能把「小时」与「分钟」传错（D18） |
| 不要求继承基类 | 业务方在自己的数据类上「实现约定」即可，不侵入业务模型 |
| 提供独立状态覆盖 | 业务方如需自定义「已过期」判断（如按任务状态而非时间），可显式声明 |
| 除时间外均提供默认实现（v1.3） | 「是否已过期」「显示内容」「业务色」三项均有默认值，业务方**只声明开始时间、结束时间、唯一标识**即可接入；新增可选字段不会破坏既有实现 |

> **业务色为何不并入 §7.3 的 17 项语义色项**：那 17 项是组件主题色，深浅两套取值由 `values` 与 `values-night` 资源承担，且 §7.3 硬性要求②规定组件内不得写深色分支。业务方覆盖主题色会破坏该机制。业务色是独立的第三条通道，只影响单个日程块自身。

### 9.2 业务方接入示意（非代码）

| 步骤 | 业务方需要做的事 |
|---|---|
| 1 | 在自己的日程数据类上「实现」组件的数据约定（声明开始时间、结束时间、唯一标识三个字段） |
| 2 | 如需自定义过期判断，再额外声明「是否已过期」 |
| 3 | 在页面上放置组件，指定宽高 |
| 4 | 把当天的日程列表提交给组件 |
| 5 | 视需要设置各类事件监听（点击、长按、新建、修改、删除、数据异常） |
| 6 | 视需要覆盖默认配色与尺寸配置 |

### 9.3 数据校验规则

组件对**不合规数据采取「容错 + 提示」策略，绝不崩溃**。

| 校验项 | 不合规时的表现 | 通知方式 |
|---|---|---|
| 结束时间早于或等于开始时间 | 自动按最短时长修正 | 数据异常事件中说明 |
| 结束时间晚于 24:00 | 截断到 24:00 | 数据异常事件中说明 |
| 开始时间早于 00:00 | 修正到 00:00 | 数据异常事件中说明 |
| 唯一标识重复 | 正常显示 | 数据异常事件中说明 |
| 列表为空或未提供 | 按空数据正常显示 | 无 |

> **产品原则**：渲染型组件不应因单条脏数据导致整个页面崩溃。修正行为对用户不可见（避免视觉跳变），问题通过事件回调上抛给业务方记录。

### 9.4 状态推导规则

```
当前时刻 = 业务方指定的当前时间，或系统当前时间

某日程为「已过」  ⟺  结束时间 ≤ 当前时刻
某日程为「进行中」⟺  开始时间 ≤ 当前时刻 < 结束时间
其余               ⟺  「未到」

样式选择：
  进行中  → 进行中配色
  已过    → 已过配色（底色 / 文字 / 色条 三色同时切换）
  未到    → 未到配色

状态覆盖规则（业务方可显式声明「是否已过期」）：

1. 声明为「已过期」→ 强制使用已过配色。
2. 声明为「未过期」→ **跳过「已过」判定**，继续按「进行中 / 未到」规则归类。
3. 因此不会出现「既非已过、又非进行中、却被当作未到」的矛盾状态。
4. 业务方无法直接指定「进行中」；如需该状态，通过「未过期」+ 时间落在区间内实现。
```

### 10.2 定制层级

| 层级 | 业务方可以做什么 | 是否需要改源码 | 优先级 |
|---|---|:--:|:--:|

#### 11.3.1 编辑层接管事件（v1.3 新增）

业务方按 §10.2 第四层接管编辑层时，组件额外提供以下交互点。这些是**交互通知**，不属于上表的数据变更事件，同样不携带数据落库语义：

| 交互点 | 触发时机 | 携带信息 |
|---|---|---|

#### 12.4.1 「全库覆盖率」的口径定义（v1.4 修订）

原表述「全库单元测试覆盖率 ≥ 75%」字面执行的结果是 **22%**，且该门禁从未真正阻断过任何一次提交。原因是字面口径把**结构上拿不到 JVM 单测覆盖率**的代码算进了分母：

| 代码层 | 能否被 JVM 单测覆盖 | 覆盖手段 |
|---|:--:|---|
| 核心算法（几何、吸附、布局、状态推导、事件兜底） | 能 | JVM 单测 |
| 对外契约与配置（数据契约、回调、定时器配置） | 能 | JVM 单测 |
| 绘制层（全部走 `Canvas`） | 不能 | 仪器测试 + 真机走查 |
| 资源读取层（尺寸/颜色解析、XML 属性读取） | 不能 | 仪器测试 + 真机走查 |
| 视图本体（测量、绘制、手势、编辑、无障碍） | 不能 | 仪器测试 + 真机走查 |

**修订后的口径**：分母只含「JVM 单测在结构上可覆盖」的代码（核心算法 + 对外契约与配置），并进一步排除无需测试的**结构代码**（属性读写器、接口默认空实现、编译器合成的桥接方法）。

被排除的三层由**界面自动化冒烟**门禁与真机走查负责——它们同样是发布前必须通过的检查项，覆盖并未因此减少。

**产品需知悉的局限**：百分比门禁在基准远高于阈值时，对**少量新增未测代码**天然不敏感。实测往代码中注入 119 条真实的未测逻辑，覆盖率仅从 88.79% 降至 85.91%，仍在阈值之上。因此本门禁的定位是**抓大幅退化**，防漏测依赖补充手段（结构性断言、代码评审、仪器测试）。

## 17. 已知限制

诚实披露 v1.0 的能力边界，避免业务方误判。

| 编号 | 限制 | 影响 | 规避建议 |
|---|---|---|---|
| L1 | 只支持单日，不支持跨天 | 跨天需业务方切换日期 | 业务方自行实现日期切换与数据加载 |
| L2 | 最小时间粒度为分钟 | 不支持秒级 | 业务方在数据层按需截断 |
| L3 | 不处理重复日程规则 | 每周三等需业务方预先展开 | 业务方展开为具体日程后传入 |
| L4 | 不支持日程嵌套（子任务） | 需平铺展示 | 业务方拆分或用文字表达 |
| L5 | 不提供图形化配置界面 | 需通过配置项或资源文件设置 | 参考主题定制指南 |
| L6 | 同一时刻的日程不分先后 | 全部等宽并排 | 业务方通过显示内容区分 |
| L7 | 不支持横跨多天的日程 | 需拆分到各天 | 业务方拆分 |
| L8 | 不做数据持久化 | 刷新页面数据需重新提交 | 业务方自行管理 |
| L9 | 不支持平板分栏视图 | 平板上仍为单列 | v2.0 规划 |
| L10 | 拖拽不支持跨天移动 | 边界处不可继续拖出 | 业务方可用「改日期」流程 |

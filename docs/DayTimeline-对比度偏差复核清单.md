## 1. 要复核什么：一项色值

| | |
|---|---|
| 色项 | `day_timeline_block_text_past`（**已过态**日程块文字） |
| 浅色取值 | `#949CA6` ← **本次复核对象** |
| 其所依托的底色 | `day_timeline_block_bg_past` 浅色 `#F1F4F7` |
| 实测对比度 | **2.51 : 1** |
| 深色取值 | `#8A929C`（**本次无需复核**，落在门禁要求的区间内） |

**含义**：过去的日程用低对比度表达「已失效」。当前 2.51:1 能看出弱化，但弱化得偏多，
在浅色底上读起来吃力。

## 2. 为什么卡住：门禁判不了，只能登记

- PRD §7.3 对这一项只给了**定性**要求——「**低对比度**，体现已失效」，**没给数值门槛**。
- 因此它既**不算不合格**（无法判失败），也**不能装作没看见**。
- 现登记在 `library/build.gradle.kts` 的 `acceptedContrastDeviations` 里，
  **每次跑 `verifyColorsFinalized` 都会照常打印这一行**，直到复核完成为止。

**换句话说：这不是缺陷，是一条挂着的待办。研发不会自行改色值**——
就地改色等于绕开设计评审，正是当初 M0-1 产生占位值的同一个教训。

## 3. 请设计在三种结果中选一个

| 选项 | 需要做的 | 后果 |
|---|---|---|
| **A. 调整取值** | 把浅色 `block_text_past` 改到 ≥ 3.0:1 | 一句话给出新 hex 即可。研发改 `设计侧定稿交付.md` + `colors.xml`，门禁随即转绿 |
| **B. 维持现状** | 回一句「2.51:1 就是有意为之」 | 研发把该项转为**正式豁免**并记录理由，门禁不再每次打印 |
| **C. 明确数值门槛** | 补一句「低对比度不得低于 X:1」 | 以后所有色项可自动判定，不再需要逐条挂待办 |

> **建议值：`#868E98`（3.00 : 1）**——与 `#949CA6` **同色相、向暗一档**，不改色相、不改风格倾向。
>
> 沿革供参考：紫色系那版是 `#9A949E`（2.63 : 1，建议 `#8F8994`）；改蓝色系后
> 变成 `#949CA6`（2.51 : 1），**略微更差一点**——蓝色系整体偏冷偏暗，
> 这一项跟着底色一起暗了。若非有意为之，建议按 A 处理。

## 4. 复核后研发会做什么（供你判断影响面）

1. 更新 `docs/DayTimeline-设计侧定稿交付.md` 的 17 项定稿表；
2. 更新 `library/src/main/res/values/colors.xml`（及 `-night` 对照项）；
3. 从 `acceptedContrastDeviations` 中移除该条目；
4. 跑 `:library:verifyColorsFinalized` 确认转绿。

> **注意**：色值门禁 `verifyColorsFinalized` 会核对「设计交付文档」与「代码取值」两处**完全一致**。
> 所以只改代码不改文档（或反之）都会被它拦下——这是有意的，
> 避免「文档说一套、代码是另一套」再次发生。

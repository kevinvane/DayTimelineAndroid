## 1. A：调整取值

浅色 `day_timeline_block_text_past` 由 `#949CA6` 调整为 **`#858D96`**。

| | |
|---|---|
| 调整后 | `#858D96` 对 `day_timeline_block_bg_past` 浅色 `#F1F4F7` ≈ **3.05 : 1** |
| 深色 | `#8A929C` **不变**（5.20 : 1，本就达标） |
| 与常规文字的关系 | 常规文字 13.08:1，「已过态」仍**明显弱于常规**，失效语义保留 |
| 色相 | 不变，仍在蓝色系内，向暗一档 |

12sp 下可读性达标，同时弱化语义不变——这是要的平衡点。

## 2. 为什么不是 B（维持现状）

B 是「回一句『2.51:1 就是有意为之』」。不采纳的原因是：**弱化的表达已经生效了，不靠更低的对比度**。
2.51:1 弱到读起来吃力，这已经越过「弱化」的收益区间，进入「看不清」的损失区间。

## 3. C：把「低对比度」定为数值门槛

§7.3 里「低对比度」此前只有定性描述，**无数值**。这是本次真正要修的东西：

> **「低对比度」正式定为不得低于 3.0 : 1。**

为什么这条比改一个色值更重要：没有门槛时，一项「偏低但可能有意为之」的取值
**判不了对错**——判失败是无据，研发自行调色是绕开设计评审。于是只能挂成待办，
每次跑门禁打印一次，直到有人来问。门槛一明确，后续同类色项可自动判定，**不必再逐条挂起**。

## 4. 研发落地情况

A + C 已改完，`verifyColorsFinalized` 转绿：**34 个取值一致 + 对比度全部达标 + 0 项登记偏差**，
其中 `block_text_past / block_bg_past` 浅色 **3.04:1 ≥ 3.0 PASS**。

> 研发对 3.05 做了**独立验算**得 **3.0449**，与设计报的 3.05 差在舍入方向，不影响判定。

三处同步，缺一不可：

| 位置 | 改动 |
|---|---|
| `docs/DayTimeline-设计侧定稿交付.md` | 定稿表第 8 行 + 浅色 `<color>` 片段：`#949CA6` → `#858D96` |
| `library/build.gradle.kts` 的 `designFinalColors` | 同上 |
| `library/src/main/res/values/colors.xml` | 同上（`values-night` 未动） |
| `library/build.gradle.kts` 的 `acceptedContrastDeviations` | 移除该项 → `emptySet<String>()` |
| PRD §7.3 | 「低对比度」补上数值下限 **≥ 3.0:1**（C） |

> **一处教训值得留下**：研发首轮改值时**漏了 `designFinalColors` 登记表**，
> 门禁立刻报「浅色文件=#858D96 设计定稿=#949CA6 色值与设计定稿不一致」并转红。
> 这正是三处同步机制该有的样子——KDoc 承诺「三者缺一都会失败并指出缺哪一处」，
> 它照做了。**这套门禁拦住了一次真实的漏改。**

## 2. 覆盖率

### 2.1 实测值

| 门禁 | 要求 | 实测 | 指令数 | 结论 |
|---|---|---:|---:|:--:|
| `verifyCoreCoverage` | ≥ 90% | **93.34%** | 2507 / 2686 | 通过 |
| `verifyAllCoverage` | ≥ 75% | **89.61%** | 3348 / 3736 | 通过 |

### 2.2 口径（必读，否则会误读上表）

「全库覆盖率」不是字面意义的全库。字面执行的结果是 22%，且该门禁从未真正阻断过任何一次提交——
原因是字面口径把**结构上拿不到 JVM 单测覆盖率**的代码算进了分母：

| 包 | JVM 单测能否覆盖 | 原因 |
|---|:--:|---|
| `core` | 能 | 纯 Kotlin，零 `android.*` 依赖（AD-02） |
| `api` | 能 | 纯数据契约 |
| `paint` | 不能 | 全部走 `Canvas` 绘制，需真机 |
| `internal` | 不能 | `Dimens.resolve` / `ConfigFromAttrs` 读 `Resources` |
| 根包（`DayTimelineView`） | 不能 | 测量 / 手势 / 编辑 / 无障碍，需真机 |

被排除的三层由 **115 条仪器测试**（`:library` 108 + `:app` 7）与真机走查覆盖。
完整口径定义见 PRD §12.4.1，该修订已获产品认可。

### 2.3 两条必须一并引用的局限

1. **仪器测试的执行数据不并入 JaCoCo JVM 报告。** 因此上表**看不到** View / 绘制 / 资源读取层的执行情况。
   补上需要 `jacoco-android` 等第三方插件，与 K10「零第三方依赖」冲突，待单独评估。
2. **百分比门禁对少量漏测天然不敏感。** 实测往 `EditResult` 注入 5 段共 119 条真实的未测逻辑，
   覆盖率仅从 88.79% 降到 85.91%，**仍在 75% 之上**。因此该门禁的定位是「抓大幅退化」而非「抓漏测」；
   防漏测靠的是结构性断言（例如 `TimelineConfigTest.mergedWith 覆盖全部可配置字段` 直接比对字段集合，
   新增字段忘合并即刻失败，不依赖任何阈值——该测试在历史上实测抓出 `autoLocateOnFirstShow` 漏合并的真实缺陷）。

### 3.2 「余量 55 倍」这句话不能直接当作安全结论

必须与下表一并阅读，否则会得出「4ms 预算已经用掉不到 2%，所以算法随便写都行」的错误推论。

**回滚验证实测**：把 `OverlapLayoutEngine.assignColumns` 的贪心首次适配
（`O(n × 最大同时重叠数)`）换成「每次从第 0 列全量重扫并对每列做两两区间比较」后：

| 断言 | 退化前 | 退化后 | 是否转红 |
|---|---:|---:|:--:|
| 全量布局 200 条（真实分布）≤ 4ms | 0.064ms | **1.10ms** | **否**（涨 17 倍，仍在预算内） |
| 列表增量更新 100 条 ≤ 16ms | 0.032ms | **0.19ms** | **否**（涨 6 倍） |
| 增长形状 `T(400)/T(200)` < 3.0 | 2.06 | **3.66** | **是** |

结论：**绝对耗时类门禁的余量有 3.6–62 倍，中等程度的算法复杂度退化在它下面不会触发红灯。**
真正咬住复杂度回归的是配套的增长形状断言，两者必须成对存在，删掉任何一条都会让另一条失去意义。

另有一条反直觉的实测：**「200 条完全同时」这组数据对算法退化最不敏感**——
退化实现的内层循环在全部重叠时第一次比较就 `break`，耗时几乎不变（0.072ms vs 0.072ms），
而同一处退化在真实分布上涨了 17 倍。三组数据集因此必须并存：最坏情况卡上界、真实分布卡灵敏度、
固定重叠卡增长形状。

### 3.3 「不收敛的重绘循环」是怎么被守住的

§12.1 的耗电项此前**原理上无法观测**：既有 102 条仪器测试全部是「裸 Context + `measure`/`layout`」，
组件从未 attach 到窗口——那种 View 上的 `invalidate()` 不调度任何绘制，
`ViewTreeObserver.OnDrawListener` 一次都不会触发。现已新建测试宿主窗口，把组件真正挂进窗口后数真实帧数。

回滚验证实测：

| 破坏方式 | 结果 |
|---|---|
| `requestRefresh` 去掉渲染签名比对，改无条件 `invalidate()` | 收敛用例转红：刷新前 **1 帧**、刷新后 **2 帧** |
| `nowTicker` 改为每 200ms 无条件重绘 | 静止用例转红：2 秒内 **1 帧 → 11 帧** |
| 删掉 `submitEvents` 的 `if (newEvents == events) return` | **仍全绿**——挡住重绘的是签名比对，不是那句提前返回；提前返回只省掉重排分栏的开销 |

> 第一条只 +1 帧而不是 +50 帧，是因为 Android 会把同一个主线程任务里的多次 `invalidate`
> 合并成一帧。所以这两条用例断言的是「**有没有出现意外的一帧**」，不是帧数多少。
> 它们抓得住「自我触发的重绘循环」，抓不住「一帧里画了几次」。

### 3.4 「网格区常驻界面元素数 = 0」是怎么被守住的

§12.1 该项原先的验证方式只写着「代码走查」——人工走查挡不住下一次改动：
任何人为了「让块能点得准 / 能做无障碍焦点」而往时间轴里塞一个子 View，
静态检查不报错、单测全绿、真机也看不出异常，指标却已经悄悄破了。

现两侧同时守着：**编译期**由 `:library:verifyNoChildViews` 扫描 `src/main` 的 12 个创建/挂载标记
与全部布局资源（**对话框不拦**——删除二次确认与表单面板是独立 window，不常驻在时间轴里）；
**运行时**由仪器测试在挂进真实窗口后遍历视图树。
回滚验证：注入一个含 `addView` / `TextView` 的子 View → 编译期门禁转红并逐条指名。

#### 4.1.2 P4 采集工具的能力边界：为什么最后必须用真手指

自动化采集这条路**试过并放弃了**，记录在此以免下一个人重走。
已确认**输入本身是通的**——普通点击有回调（`点击 gen_137 → 弹详情`），
2 秒静止长按也进编辑态（`长按 gen_137 → 进入编辑态`）。卡住的是**采集手段**：

| 尝试 | 结果 |
|---|---|
| `input swipe x y x y 1200`（静止长按） | 无回调（长按阈值比 1.2s 长） |
| `input swipe x y x y 2000`（静止长按 2s） | ✅ 触发长按 |
| 6 秒长拖、总位移仅 10px（远慢于 touch slop） | 无回调 |
| 多段 2px 慢速拖动 | 无回调 |
| `input motionevent`（可逐帧注入的连续手势） | **API 28 上不存在该子命令** |

§12.1 要的是「拖动一条日程块**平移** ≥ 5s」，即**一次手势内先按住、再持续位移**。
`input swipe` 的位移是线性插值，无法表达「前 800ms 静止、随后移动」。

剩余路径是 `sendevent` 手工拼 `/dev/input/eventX` 的原始事件流，
但**那条路测出来的数字里有多少是组件的、有多少是注入器的时间误差，分不清**——
用它给出「≤ 1 帧」的结论会是一个看起来权威、实则掺了测量误差的数字。

**最终解法**：既然注入器表达不了这个手势，就让**人的手指当注入器**——
采集端只负责 `reset` 与读取，逐帧数据仍是设备自己记的，**不含任何注入器时间误差**。
这正是 §4.1.3 那组数据的来源。

#### 4.1.3 P4 拖拽跟手延迟：真手指拖动 + 帧级数据

**采集方式**：人用**真手指**持续拖动日程块，采集端在拖动前
`dumpsys gfxinfo <包名> reset`、拖动后读 `framestats`，对每一帧算

```
输入延迟 = FrameCompleted − NewestInputEvent
```

即「**最新一次触摸事件发生后，到这一帧真正呈现**」的间隔。
只统计 `NewestInputEvent > 0` 的帧（120 / 120 全部带输入，无静止帧混入）。

> **为什么必须用真手指**：`adb shell input swipe` 的位移是线性插值，
> 表达不出「先按住、再连续平移」这个手势；`input motionevent` 在 API 28 上不存在。
> 而**手指是真实注入的触摸**，采到的延迟是有效的。
> 详见 §4.1.2 的完整尝试记录。

| 指标 | 实测 | 目标 | 结论 |
|---|---:|---|:--:|
| 中位数 | **12.10 ms** | ≤ 16.7ms | 通过 |
| **P95** | **15.20 ms** | ≤ 16.7ms | 通过 |
| 最大值 | **15.97 ms** | ≤ 16.7ms | 通过 |
| **超过 1 帧的帧占比** | **0 / 120（0.0%）** | 0% | 通过 |

全部 120 帧落在 **10.1–16.0 ms** 这个窄带内，无一突破一帧预算。

整场拖拽的汇总（同一次采集，`dumpsys gfxinfo` 自带统计）：

| 指标 | 值 |
|---|---:|
| 总帧数 | 883 |
| 卡顿帧 | 3（**0.34%**） |
| 帧耗时 P50 / P95 / P99 | 7 / 10 / 13 ms |
| Missed Vsync | **0** |

> ⚠️ **两组数字的口径不同，不可混用**：
> `framestats` 只保留**最近 120 帧**的滚动窗口，故逐帧明细是拖拽**末段约 2 秒**；
> 而 883 帧 / 0.34% 是**整场**拖动的汇总（gfxinfo 自带计数不受窗口限制）。
> 本报告把两者分开列，未合并成一句「P95 = 15.20ms、掉帧 0.34%」。

> **一处采集副作用必须记录**：让人工能拖动，demo 的长按**不弹表单**，

> **这种模式下拖完松手等于放弃，没有任何确认入口**。

#### 4.1.4 一次「差点记成缺陷」的排查

人工初判「拖到整点/半点附近没有对齐吸附」。**这与 §7.2（吸附 15 分钟）、
D11（上下对称）冲突，若直接记为缺陷会开出一条假缺陷单。** 排查过程：

1. 查实现——`SnapCalculator.snapMove` 对齐开始时间、保持时长，算法正确；
   `SnapCalculatorTest` 已覆盖算法本身**含 D11 上下对称**（`SnapCalculatorTest:49-50`）。
2. 查接线——`DayTimelineView.dragTo` **无条件**调用
   `session.moveTo(..., dimens.snapMinutes, ...)`，没有按模式分支。
3. 查配置——demo 布局 `app:dtSnapMinutes="5"`，属性名与 `ConfigFromAttrs` 一致。
4. **做看得见的实验**——把步长临时改成 **60 分钟（整点）**再拖：
   块**猛地吸到 14:00 / 15:00**。

**结论：吸附接线完全正常，问题是 5 分钟步长在真机上不可感知。**
格高 64dp 下 5 分钟 = 5.33dp，在 density 2.6 的真机上约 **14px**，
人工慢拖察觉不到。库内默认 `day_timeline_snap_minutes` = **15**（约 42px，可感知）。

> demo 已把 `dtSnapMinutes="5"` 的原因写进 `activity_main.xml` 注释，
> 并注明「想让 demo 演示出吸附效果，建议改用 15 或更大」。
> **这属于 demo 的取值选择，不是组件缺陷**——组件默认 15 分钟是可感知的。
>
> 这次排查的教训值得单列：**「人工反馈某行为没发生」与「该行为有实现」之间，
> 必须先做一次「让该行为变得显眼」的实验再下结论**，
> 否则会为不存在的问题开单，而假缺陷单消耗的信任比漏报更贵。

#### 4.1.6 顺带查清的自动化空白：「真实拖拽 → 吸附」无覆盖

排查 P4 时发现：`SnapCalculator` 的**算法**有测试，但**没有任何一条测试断言
「手指拖完之后落点确实被吸附到了步长上」**——算法对、接线断，中间那层没人守。

尝试补自动化，**三轮均失败**，且三次红的原因各不相同、没有一次红在吸附断言上：

| 轮次 | 红的实际原因 |
|---|---|
| 1 | `MotionEvent.obtain` 给 DOWN 与 MOVE 填了同一个 `eventTime`，800ms 后的 MOVE 看起来是 0ms，长按判定等不到超时 → 块没动 |
| 2 | 改为真实递增时间戳后，**在 `ACTION_UP` 之后才读**；而草稿未确认就抬起时编辑态被丢弃、位置还原 → 又读回原始值 |
| 3 | 改到 MOVE 之后、UP 之前读 → 仍读到原始分钟，**块在拖动过程中确实没动** |

根因：长按依赖 `Handler` 延迟回调与真实窗口的配合，而该测试宿主是
「裸 Context + `measure`/`layout`」，组件从未 attach 到窗口——
与本仓库 `RedrawConvergenceTest` 当初遇到的是同一类问题（那里靠新建
`TimelineTestHostActivity` 解决）。

该用例已建为 `DragSnapWiringTest` 并标 `@Ignore`，
**类 KDoc 里完整记录了上述三轮失败过程与解锁条件**。
选择保留而非删除，是为了让「真实拖拽无自动化覆盖」这个空白写在代码里，
而不是只留在某次对话里。

> **2026-10-13 更新：本节三行原为「零覆盖」，现已补上自动化，但过程中查出一处真实缺陷。**
>
> 原先「RTL / 字体缩放 / 旋转」三项**全仓库零测试覆盖**。补齐时第一版 RTL 用例直接转红，
> 失败信息是「期望 RTL、实得 LTR」。加探针分清责任后发现：**连原生 `View` 在同一环境里
> 读回来也是 LTR**（游离 View、属性赋值、`setLayoutDirection(1)`、挂进 ViewGroup 后再设，
> 四种写法全部返回 0）。根因是清单里少了一行 `android:supportsRtl="true"`——
> **不声明它，Android 框架强制 LTR，`setLayoutDirection(RTL)` 是空操作**。
>
> 后果比「测试写错」严重：**AD-10 的镜像实现一直是对的，但在此之前没有任何一处让它真正生效过**。
> demo 应用声明了这一项所以能用；**组件库无法替接入方写进清单**，因此接入方不声明就会静默退化为 LTR。
> 已在 `library/src/androidTest/AndroidManifest.xml` 补上该声明，并在 README 与接入文档中写明这是接入方的前置条件。
> 本项本身仍需真机验证（§4.3 状态列），但「镜像逻辑没生效」这一类缺陷今后不会再无声潜伏。

> **RTL 零覆盖的教训（已修复，留档）**：D13 把「须支持 RTL」列为硬性约束（§12.2），
> AD-10 给出的方案是绘制层镜像，但**全仓库唯一一行 RTL 逻辑
> `DayTimelineView.resolveAxisEnd` 在任何测试中一次都没被调用过**。
> 2026-10-13 补测试时才发现：镜像实现本身是对的，真正的问题是**清单里没有
> `android:supportsRtl="true"`**，框架因此强制 LTR。也就是说这项「支持」从未真正生效过。
> 同类零覆盖的**字体放大 200%** 与**横竖屏旋转**同日一并补上。
>
> **判据总结**：当一个能力的实现只有一行、且那行的正确性依赖调用方是否做对某件准备时，
> 「代码存在」与「能力可用」之间隔着一整个使用前提，而现有门禁对这类前提**完全无感**。
> 补测试时用探针先分清责任方（原生 View 同样失败 → 是环境/前提问题，不是组件问题），
> 比反复改断言有效得多。

### 7.1 §12.1 性能采集的实际命令（2026-10-14 真机）

```powershell
# 目标设备（经 WiFi ADB 连接的真机 Pixel）
$d = '192.168.0.24:5555'
$pkg = 'com.github.kevinvane.daytimeline.app'

# P1/P2：每次冷启动，取 onCreate → 首帧 onPreDraw 的耗时（130 次）
adb -s $d shell am force-stop $pkg; adb -s $d logcat -c
adb -s $d shell am start -n $pkg/.MainActivity --ei event_count 200 --ez first_frame_ms true
adb -s $d logcat -d -s DayTimelineDemo:I     # 读 FIRST_FRAME_MS=... event_count=200

# P3：连续滚动 60s 前先清零帧统计，再读 Android 自带的 Janky frames
adb -s $d shell dumpsys gfxinfo $pkg reset
adb -s $d shell "for i in $(seq 1 75); do input swipe 540 1200 540 700 200; input swipe 540 700 540 1200 200; done"
adb -s $d shell dumpsys gfxinfo $pkg

# P5：每 5 分钟采一次内存
adb -s $d shell dumpsys meminfo $pkg

# P6：起点清零、终点导出（本轮因设备插电而无效）
adb -s $d shell dumpsys batterystats --reset
adb -s $d shell dumpsys batterystats
adb -s $d shell dumpsys battery                # 确认供电状态
```

> **两个必须随数据一并引用的采集坑**：
>
> 1. **`svc power stayon true` 会把屏幕钉亮**，耗电统计因此包含全部屏幕时间；
>    本轮 P6 更大的问题是设备直接插着充电（`AC powered: true`），
>    重跑时必须拔掉充电线，并**先用 `dumpsys battery` 确认 `AC powered: false`** 再开始。
> 2. **PowerShell 5.1 读 `.ps1` 按 ANSI 处理**，无 BOM 的 UTF-8 脚本里中文会被解成乱码并
>    破坏语法（本次脚本因此瞬间跑完、日志出现乱码）。
>    采集脚本一律写成**纯 ASCII**，或存为带 BOM 的 UTF-8。

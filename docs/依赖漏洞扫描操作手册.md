# 依赖漏洞扫描 · 操作手册

> **本文档解决一件事**：把 `:verifyNoHighVulns` 这道门禁**真正跑通一次**。
> 门禁本身在 2026-10-13 已建立（commit `a477f0f`），但**一次都没跑通过**——
> 首次全量漏洞库同步始终卡在「本机到 NVD 的链路被限流」。本文档就是为此写的。
>
> **本文档尚未提交 git**，等跑通后再决定去留。

## 0. 先看这里：当前状态与事实基础

| 项 | 状态 |
|---|---|
| 门禁实现 | ✅ 已完成，`verifyNoHighVulns` + CI `dependency-scan` job |
| NVD API key | ✅ 你已申请并确认邮件，**key 有效**（实测 HTTP header 认证返回 200） |
| **实际跑通** | ❌ **没有**。跑过 4 轮全部失败，原因见 §5 |
| **「0 个高危漏洞」的结论** | ❌ **没有任何实测支撑**，文档里一律写「尚未跑通」 |

本文档里带「**已实测**」标记的结论，都是在这台机器上跑出来的；**没跑通之前，
§6 中标注「预期」的内容属于推断，第一次跑完请回来校正。**

## 1. 跑之前你要知道的三件事

1. **首次同步很慢**：NVD 全量漏洞库约 700MB，官方口径 30–45 分钟。中间长时间无输出是正常的。
2. **不要频繁中断**：中断会丢掉进度，下次要从头再来。
3. **别在旁边反复探测 NVD**：诊断用的请求会消耗同一份限流额度，我这次就是自己把额度打爆的
   （见 §5.3）。想看进度就查本地缓存目录（§3.3），不产生任何网络请求。

## 2. 本地跑（推荐路径）

### 2.1 第 0 步：设环境变量

```powershell
$env:NVD_API_KEY = "<your-key>"
```

- 仅对**当前 PowerShell 会话**生效，关闭即失效。
- **不会**写进任何文件——门禁是从环境变量读的，不读配置文件。
- 门禁会先跑 `verifyNvdApiKeyPresent` 检查它；没设的话会直接给出这段提示并退出（**已实测**：40 行输出、2 秒结束）：

  ```
  依赖漏洞扫描需要 NVD API key，而当前环境变量 NVD_API_KEY 为空。
  ...
  ```

> 不设 key 也能让门禁往下走，那样会看到一屏 Java 堆栈（430 行，**已实测**），
> 末尾是 `Invalid API Key, length of 0 too short`。**不必尝试**，那是 13.x 的已知表现。

### 2.2 第 1 步：先只跑一个模块，把漏洞库缓存填满

```powershell
.\gradlew.bat :library:dependencyCheckAnalyze
```

**为什么要分两步**：三个模块各自持有 `dependencyCheckAnalyze` 任务，
一步到位会让它们**各去更新一次**漏洞库，等于三倍请求、更容易撞限流。
先跑 `:library` 填满共享缓存（`.gradle\dependency-check-cache`），后面的模块就直接命中缓存。

### 2.3 第 2 步：跑完整门禁

```powershell
.\gradlew.bat verifyNoHighVulns
```

这一条会做四件事（任务图**已用 `--dry-run` 核实**）：

1. `verifyNvdApiKeyPresent` —— 前置检查，缺 key 立即拦下
2. `:library` / `:app` / `:r8test` 各自的 `dependencyCheckAnalyze`
3. `dependencyCheckAggregate` —— 汇总三份报告
4. 按 **CVSS ≥ 7.0**（高危 + 严重）判定是否失败

> **两个必须显式接线的地方**（不实测发现不了，都是踩过的坑）：
> 插件若只装在根项目上，子模块根本没有扫描任务；即便都装了，
> `dependencyCheckAggregate` **也不会**自动把它们纳入任务图，
> 只 `dependsOn` 它会「汇总一份空报告然后通过」。

想一次跑完也可以（更容易撞限流）：

```powershell
.\gradlew.bat verifyNoHighVulns
```

## 4. 走 CI 跑（推荐的最终落法）

本机链路被限流的话，**首次全量同步应该在 CI 里完成**——
GitHub Actions 的出口 IP 与本机不同，限流计数也相互独立。

### 4.1 配置 secret（必做，一次性）

1. 打开仓库：`https://github.com/kevinvane/DayTimelineAndroid/settings`
2. 进 **Secrets and variables → Actions**
3. 点 **New repository secret**
4. 填写：
   - **Name**：`NVD_API_KEY`（**必须一字不差**，yml 里引用的就是这个名字）
   - **Secret**：`<your-key>`
5. 保存

> 用 Environment secret 也行（Settings → Environments → 对应 environment → Secrets），
> 但必须确认该 workflow 的 job 声明了对应的 `environment:`，否则不会生效。
> **当前 `dependency-scan` job 没有声明 environment，用 repository secret 最省事。**

### 4.2 触发

把 `dev` 分支推上去即可（当前所有提交都还在本地 `dev`，未推送）：

```powershell
git push -u origin dev
```

`dependency-scan` 是独立 job，与静态门禁 / 仪器测试 / R8 并行，互不阻塞。

### 4.3 CI 上这个 job 已经配好的东西

| 项 | 配置 |
|---|---|
| job 名 | `dependency-scan` |
| 漏洞库缓存 | `actions/cache` 缓存 `.gradle/dependency-check-cache`，key 含 `libs.versions.toml` 的哈希 |
| 报告归档 | `upload-artifact`，名 `dependency-check-report`，保留 7 天 |
| 失败时 | 打印 CVSS ≥ 7.0 的漏洞明细（依赖名 + CVE 号 + 描述） |

**首次 CI 运行同样要 30–45 分钟**（缓存在第一次之后才生效），别以为卡死。

### 4.4 从 CI 拿报告

1. Actions 页 → 失败的 `dependency-scan` → 点进去
2. 直接看日志末尾的**漏洞明细**（失败时自动打印）
3. 要完整报告：在页面底部 **Artifacts** 下载 `dependency-check-report`（zip），
   解压后取 `dependency-check-report.html` 用浏览器打开

## 5. 失败了怎么读（4 轮排查的结论）

### 5.1 错误对照表

| 现象 | 含义 | 处理 |
|---|---|---|
| `依赖漏洞扫描需要 NVD API key`（40 行、2 秒） | 环境变量没设 | §2.1 |
| `Invalid API Key, length of 0 too short` + 一屏堆栈（430 行） | 同上，但前置检查被绕过了 | 不用管，见 §2.1 的说明 |
| `NvdApiRetryExceededException: ...unsuccessfully five times` | **链路被限流**，不是 key 问题 | 退避 5 分钟后重试；反复出现就走 CI（§4） |
| HTTP 503 | 同上，NVD 侧限流 | 同上 |

### 5.2 已排除的三个「疑似原因」（别再重复排查）

1. **key 没生效？** 已排除。实测同一 key：`query param → 404`、`HTTP header → 200`；
   而**随机伪造的 key 走 header 同样是 404**，据此确认 key 有效。
2. **客户端用错传参方式？** 已排除。`javap -c` 反编译 `open-vulnerability-clients` 9.0.6 的
   `NvdCveClient`，字节码是 `ldc "apiKey"` → `getfield apiKey` → `SimpleRequestBuilder.addHeader(...)`，
   **走的就是 header**。
3. **NVD 强制要 key？** 不准确。实测**不带 key 反而返回 200**（匿名可用，只是限速 5 次/30 秒）；
   插件失败是因为客户端会**主动发一个空 key**，空 key 被当成「查无此 key」拒绝。

### 5.3 真正的卡点（本机跑不通的原因）

退避后重跑的现象（**已实测**）：

- 运行 **44 分钟**仍停在 `Checking for updates and analyzing dependencies for vulnerabilities`
- 期间 **20 秒内 CPU 仅增长 0.1 秒** → 纯等网络，没在干活
- 保持 **7 条** ESTABLISHED 的 443 连接
- `.gradle\dependency-check-cache` **始终未被创建**

同一调用用 .NET 的 HTTP 栈能拿到 200，但 dependency-check 的 Apache HttpClient 5
在长时间运行中拿不到有效响应。**结论：本机（开发环境）到 NVD 的出口被严重限流。**

> 我自己把额度打爆过一次：排查时连续发了约 10 次对照请求（含插件每轮 5 次重试），
> 随后所有请求都变成 503，退避 240 秒才恢复。**排查时请节制探测。**

### 5.4 一处未经端到端验证的调整

`build.gradle.kts` 里把 `nvd.maxRetryCount` 调到 20、`nvd.delay` 保持 8 秒，
理由是默认的 5 次重试在连续 503 下会立刻放弃。
**这两个值没能端到端验证**（运行始终没跑完），只是「更宽容」而不是「已验证有效」。
第一次跑通后如果仍然频繁失败，可以继续调大；代码注释里已标明这一点。

## 7. 安全注意

- **不要把 key 写进任何仓库文件**（`build.gradle.kts` / `ci.yml` / 文档 / 脚本）。
  门禁从环境变量读，CI 从 secret 读，两条路都不需要把 key 落盘。
- 命令里带 key 会进入 PowerShell 的历史（`Ctrl+↑` 就能翻出来）。
  更稳妥的写法：本机用 `$env:NVD_API_KEY = (Read-Host -AsSecureString | ConvertFrom-SecureString -AsPlainText)`，
  或者干脆只在 CI 里配 secret、本机不跑。
- 这个 key 已经出现在过聊天记录与本次会话的命令行里。若聊天日志会被留存，
  视同已泄露——NVD 免费 key 权限很低（仅放宽限速），但**发现异常应到 NVD 后台重新签发**。
- 临时脚本、日志文件用完即删；本次排查产生的 565MB / 91MB debug 日志已删除。
